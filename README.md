# SDLC Factory

> 状态：OpenCode 生命周期插件完整产品已实现并通过真实目标项目验收
>
> 更新日期：2026-08-13

SDLC Factory 是一个安装到目标项目中的本地优先 OpenCode 生命周期插件。它以真实项目资料、持续多轮对话和显式 `/sdlc-*` 命令为入口，把需求、设计、编码、测试和系统验收组织成可追溯、可恢复、可人工审核的研发过程。

AI 负责阅读资料、分析问题、提出候选和生成草案；用户负责业务决定和正式审核；系统负责保存版本、内容哈希、执行记录和测试证据。AI 的文字结论不能自行成为已批准事实。

## 0. 文档权威

当前正式约定按以下顺序解释：

1. 本 README：产品目标、使用方式和总边界；
2. [CONTEXT.md](CONTEXT.md)：统一业务语言；
3. `docs/design` 中按编号排列的正式设计；
4. `docs/research`：研究证据，仅解释来源，不自行升级为产品决定；
5. `packages/opencode-plugin`：当前插件实现和自动化验证；实现必须持续符合上位正式设计。

当实现、旧研究结论或历史提交与正式设计冲突时，以本 README、`CONTEXT.md` 和编号设计为准。旧的能力单元、单一需求文档和逐能力单元执行模型已经废止，不再保留兼容语义。

## 1. 核心目标

### 1.1 解决的问题

Factory 要解决以下问题：

- 大型需求文档一次进入模型后容易遗漏、混淆和超出有效上下文；
- 需求、设计和测试经常使用不同的拆分单位，导致追溯断裂；
- AI 容易把推断、待办项或执行结束误写成正式完成；
- 外部接口地址、环境、凭据引用和测试结果缺少精确记录；
- 系统测试若临时生成测试和反复读取全量日志，会造成不必要的模型调用成本；
- 项目重启后需要从真实产物和记录恢复，而不是依赖对话记忆。

### 1.2 统一业务模块

项目只维护一套跨生命周期的业务模块划分：

```text
项目
└─ 业务模块：系统管理
   ├─ 功能组：用户管理
   ├─ 功能组：角色权限
   ├─ 功能组：系统配置
   └─ 需求条目
```

业务模块从需求阶段建立，并贯穿设计、编码和测试。设计阶段不再产生新的能力单元或其他平行执行单位。

如果一个业务模块大到无法独立设计、编码和测试，必须回到需求阶段，由用户确认拆分业务模块；设计阶段不得偷偷增加替代层级。

### 1.3 需求地图与版本

需求不再是一份巨大文档，而是一个由多份受控文档组成的需求集合：

```text
产品概述
+ 需求地图
+ 各业务模块功能需求
+ 外部接口需求
+ 全局和模块非功能需求
= 总需求版本
```

需求地图展示业务模块、外部接口、非功能需求和关系。视觉位置、颜色和折叠状态只是界面投影；模块、需求、作用范围和依赖变化才产生新的需求版本。

每个业务模块可以独立形成候选版本并接受人工审核。总需求版本精确引用各模块、接口和非功能需求的已批准版本，不复制正文，也不使用含糊的“最新版本”。

### 1.4 模块化设计

设计沿用同一业务模块身份：

```text
产品总体设计
+ 模块设计
+ 接口设计
+ 测试说明
= 总设计版本
```

产品总体设计只描述跨模块共享的系统结构、运行方式、数据规则、安全规则、部署规则和验证原则。每个模块设计只处理一个业务模块，并引用精确的模块需求、接口需求和非功能需求版本。

测试说明在设计阶段形成，规定需要验证什么、使用什么环境、由哪些可执行测试产生证据。低层测试细节以测试代码为准，不在 Markdown 中复制成巨大的测试用例手册。

### 1.5 编码与测试

编码和测试都以业务模块为范围：

```text
模块需求已批准版本
→ 模块设计和测试说明已批准版本
→ 模块编码
→ 编译、静态检查、单元测试、模块集成测试、接口契约测试
→ 测试记录
→ 模块代码和测试结果审核
```

测试代码在模块编码期间生成并保存。后续测试由受控执行器确定性运行，不要求 AI 每次重新生成测试。

每次 `/sdlc-code <业务模块名称>` 通过输入门槛并建立运行记录后，必须使用 OpenCode 原生 `todowrite` 建立编码待办清单，并在编码过程中持续更新。清单至少覆盖输入核对、测试先行、代码实现、相关验证和差异检查；步骤只有在对应操作和证据真实完成后才能标记完成。编码结束、中断或阻塞时，运行记录必须保存待办清单摘要和未完成原因。

OpenCode 规划模式可以用于编码前的只读分析和方案讨论，但不替代已批准的模块设计，也不替代编码待办清单。实际修改文件时进入构建模式，并以待办清单控制当前模块内部步骤。

系统测试按以下顺序执行：

1. 检查各模块测试记录是否绑定当前代码、测试代码、依赖和环境；
2. 只重新执行已失效或受影响的模块测试；
3. 启动完整应用并等待就绪检查通过；
4. 执行外部接口连通和契约检查；
5. 使用 Playwright 执行跨模块关键用户流程；
6. 自动生成系统测试报告；
7. 人工审核系统测试报告并形成系统测试版本；
8. 由确定性工具直接复用已批准系统测试版本、同一报告和同一批测试记录，形成系统验收候选；
9. 经人工审核后形成系统验收版本。

Playwright 不替代 Java、TypeScript 或其他语言的单元测试执行器。单元测试和模块集成测试使用项目原生工具；Playwright 只验证浏览器中的完整系统行为。

### 1.6 外部接口与环境

外部接口信息分层保存：

| 信息 | 保存位置 |
| --- | --- |
| 需要什么外部能力、业务约束和错误要求 | 外部接口需求 |
| 协议、路径、数据、认证、超时和重试 | 接口设计 |
| 开发、测试、生产环境的实际地址 | 环境配置 |
| 本次测试实际使用的地址和环境版本 | 测试记录 |

凭据只保存受控引用，不保存明文密码或访问令牌。测试记录可以保存令牌签发和过期时间，但不得保存明文令牌。

### 1.7 项目进度

项目进度不是独立计划或第二套生命周期状态。总设计版本批准后，系统根据需求、设计、代码、审核、运行和测试事实实时推导完整的模块级项目进度；总设计批准前，`/sdlc-status` 只显示当前生命周期阶段和缺失门槛。

项目进度只展示最新状态：

- 各业务模块当前阶段；
- 未开始、进行中、等待审核、挂起、阻塞、完成或失效；
- 精确的当前需求、设计、代码和测试版本号；
- 单元、模块和系统测试的当前结果；
- 阻塞原因和唯一建议命令。

项目进度不独立持久化、不拥有业务版本号，也不允许人工或模型直接修改。历史由候选、审核、运行、测试记录和追加式事件保存；项目进度只读取这些事实并生成当前投影。每次查询还核对已批准代码字节和测试记录中的文件指纹；代码、测试代码或工具链文件漂移后，相关模块及下游系统测试、系统验收立即显示失效。

## 2. 命令与引导

插件提供以下显式命令：

- `/sdlc-init`：初始化项目、来源目录和本地事实；
- `/sdlc-spec [业务模块名称]`：维护产品概述、需求地图或指定模块需求；
- `/sdlc-design <业务模块名称>`：维护指定模块设计、接口设计和测试说明；
- `/sdlc-code <业务模块名称>`：编码指定业务模块并维护测试代码；
- `/sdlc-test <业务模块名称>`：执行指定模块测试；
- `/sdlc-test system`：执行系统集成和 Playwright 关键流程；
- `/sdlc-review [对象名称]`：审核当前候选版本；
- `/sdlc-status`：显示当前生命周期阶段；总设计批准后同时显示完整项目进度、版本号、缺口和唯一建议命令。

命令不会自动串行执行。系统可以推荐下一条命令并投影一个“下一步待办”，但只有用户再次输入完整命令才会开始新的工作。这个单条提示与编码会话内部的编码待办清单不是同一对象。

### 2.1 最小上下文

处理“系统管理”时，只装配：

- 产品概述；
- 需求地图中的系统管理节点；
- 系统管理模块需求或模块设计；
- 相关外部接口；
- 适用的全局和模块非功能需求；
- 直接上下游模块摘要；
- 与当前问题相关的来源片段；
- 精确的输入版本和内容哈希。

跨模块检查先读取地图、摘要和结构化引用，发现问题后再按需读取相关正文。不得为了“保险”把整个项目文档一次性放入模型上下文。

### 2.2 安装与开始使用

前置条件为 Node.js 22.12 或更高版本、pnpm 10.34.5 和 OpenCode 1.18.14。插件从本仓库构建并安装到一个明确的目标项目：

```powershell
cd D:\workspace\sdlc-factory\packages\opencode-plugin
pnpm install --frozen-lockfile
pnpm build
node dist\cli.js install --target D:\path\to\target-project
```

安装器只覆盖自己管理的 `.opencode` 运行资源；如果目标位置存在未登记的同名插件文件会拒绝覆盖。升级时重复执行同一安装命令。安装器会校验旧 `revisions/` 快照的字节哈希，将其迁移为无扩展名内容对象，并保存旧路径到新对象的迁移清单；候选和已批准版本文件保持逐字节不变，读取器通过清单解析旧引用。进入目标项目启动 OpenCode 后，先执行 `/sdlc-init`，随后使用 `/sdlc-status` 获取唯一建议命令。

自动化脚本只需读取当前项目进度时，不要启动模型会话，直接在目标项目执行：

```powershell
node .opencode\bin\sdlc-status.mjs
```

该入口调用与 `/sdlc-status` 相同的确定性状态服务，只输出结构化当前事实，不产生模型 token。

## 3. 版本与审核

### 3.1 稳定身份和不可变版本

业务模块、需求条目、外部接口和非功能需求都使用稳定编号。工作草案可以修改；提交候选时固定文件清单、内容哈希、来源和父版本；候选一旦创建不可修改。

人工审核可以通过、退回或暂缓。通过后形成不可变的已批准版本；退回后必须修改工作草案并创建新候选。AI、待办项、命令结束或测试进程退出都不能代替人工审核。

### 3.2 修订记录

每次需求语义变化都追加修订记录，至少包含：

- 变更对象和稳定编号；
- 原版本和新候选；
- 变更摘要、原因和来源；
- 变更类型；
- 受影响模块、接口、设计、代码和测试；
- 用户审核决定；
- 时间和内容哈希。

变更类型包括文字整理、语义澄清、行为变化和结构变化。AI 可以提出分类和影响分析，但最终分类由人工审核确认。

### 3.3 回退

已批准历史不得删除或覆盖。回退通过创建一个新的总需求版本或总设计版本完成，新版本重新引用历史模块版本，并记录回退原因；不得简单移动指针伪装成历史没有发生。

## 4. 测试记录与报告

测试记录是权威执行事实，至少包含：

- 总需求版本、总设计版本和目标业务模块；
- 代码和测试代码内容哈希；
- 依赖模块版本；
- 环境配置编号和内容哈希；
- 实际接口地址，敏感字段脱敏；
- 执行命令、开始结束时间和退出码；
- 通过、失败、跳过和阻塞数量；
- 日志、截图、视频、Playwright 跟踪文件等证据位置；
- 运行工具和锁文件哈希。

测试报告由测试记录自动生成，只负责用户阅读和审核，不得脱离底层记录单独声称通过。

当代码、测试代码、依赖、输入版本、环境或工具链任一指纹变化时，原测试记录失效。完全一致的成功记录可以复用，以减少重复执行和模型调用成本。

系统验收不是第二次测试运行。系统测试版本批准后，`sdlc_system_acceptance_candidate_create` 在工具内部核对当前有效版本，只复用该版本的自动报告和测试记录；AI 不再重构历史命令、文件指纹或测试参数。

## 5. 产品边界与完成定义

SDLC Factory 只交付 OpenCode 项目级插件、命令、Skills、确定性工具和目标项目内的生命周期产物，范围包括：

- 模块化需求、设计和测试说明；
- 需求地图和版本修订；
- 候选、审核和已批准版本；
- 按业务模块编码和测试；
- 系统集成测试和 Playwright 关键流程；
- 最小上下文装配和中断恢复；
- 环境、接口地址和测试证据记录。

项目管理界面、独立服务端、通用任务编排器和面向多项目的门户不属于本产品。目标项目自己的 Electron、Web、Java 或其他应用只是被插件研发和测试的对象，不构成 Factory 的产品形态。

插件完成必须同时具备真实业务模块编码、原生模块测试、完整应用系统测试、Playwright 跨模块流程、系统测试审核和系统验收审核，不能只完成文档模板或核心数据合同。

## 6. 安全与事实边界

- 原始资料与 AI 生成文档分离；
- 未知、假设和缺失证据不得写成已确认事实；
- 本地文件读取受项目允许目录限制；
- 写入只允许目标项目受控路径；
- 外部命令经过权限规则和受控执行器；
- 明文凭据不得进入需求、设计、提示词、测试记录或日志；
- 原始日志、截图、视频和跟踪文件保存在证据存储，不塞入结构化项目状态；
- Markdown 保存用户可读正文，结构化状态保存编号、版本、哈希、关系、审核和证据索引。

## 8. 当前状态

当前已经完成 OpenCode 插件完整生命周期闭环：业务模块贯穿需求、设计、编码和测试；需求、设计和测试文档按模块装配；候选固定文件快照、父版本和精确输入；直接用户审核后形成不可变已批准版本；环境、受控命令、测试记录和报告分别留证；项目进度从底层事实和工作区当前字节实时推导，不再保存独立计划。

OpenCode 原生编码待办已经通过插件事件和运行门槛约束：编码运行在文件修改或命令执行前必须实际调用 `todowrite`，成功结束还需要至少五项全部完成的待办和真实命令证据。测试命令由受控工具等待进程退出并自动保存脱敏证据，不使用固定 sleep 判断完成。

当前插件自动化回归覆盖 20 个测试文件、57 项测试，包括需求与设计合同、专用测试候选、内容寻址快照、旧状态迁移、零模型状态查询、审核、状态恢复、证据指纹、漂移传播、路径边界、安装和构建产物。

真实隔离项目 `D:\workspace\sdlc-test\lifecycle-plugin-acceptance-20260811` 已从原始需求走通产品概述、需求地图、两个业务模块需求、外部接口需求、非功能需求、总需求版本、总体设计、两个模块设计与测试说明、接口设计、总设计版本、两模块编码和原生待办、30 项项目测试、完整应用打包、Playwright 跨模块流程、系统测试报告及最终系统验收。全新进程和迁移副本均能恢复状态；修改已批准代码后，依赖模块、模块测试、系统测试与系统验收会自动失效。

运行产物审计确认，完整验收项目的隐藏状态约 512 KB。145 个 JSON 分别对应候选、审核、版本、运行、命令证据、测试记录、来源和环境，数量与事实条数一致，不应合并成少数可变大文件。后续候选正文改为按 SHA-256 内容复用；模块测试、系统测试和系统验收均使用专用确定性入口，避免重复快照和模型重构历史参数。详见 [DESIGN-04](docs/design/04-plugin-artifact-quality-design.md)。

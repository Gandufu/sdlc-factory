A. 整体 Fork Open Design

直接以官方 daemon 为底座，删除设计专属功能，再嵌入 Factory 生命周期。

优势

  • 最快获得现成 UI/会话/CLI 代码
  • 初期演示速度高

代价

  • 弱治理语义深入原实现
  • 升级、许可证、权限整改面大

B. 提炼 Runtime Kernel，重建 Factory Core

只提炼 Open Design 成熟的小模块与测试向量；围绕 Factory 需求重建深模块与权威合同。

优势

  • 复用关键源码又不继承错误领域语义
  • 单一数据库、清晰 seam、可验证

代价

  • 首个纵切比 Fork 慢
  • 需要重写产品领域与迁移工具

C. 双 daemon Sidecar

Factory 只做治理，把 Open Design 原样作为会话与 Runtime Provider。

优势

  • 最少改官方源码
  • 可快速跟随 Runtime 更新

代价

  • 双数据库与双权威投影
  • 内部 API、权限和审计链不稳定
推荐

B — 提炼机制，不 Fork 产品

它最符合“需求权威”：复用 Runtime Registry、Adapter、Resume Guard、安全 staging/解包的机制与测试，但由 Factory 自己拥有 Conversation、Invocation、Gate、Baseline、Evidence、Memory 和权限事实。

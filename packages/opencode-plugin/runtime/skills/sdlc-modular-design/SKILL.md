# 模块化设计与测试说明

## 输入门槛

先调用 `sdlc_status`。目标模块需求、相关接口需求、非功能需求和总需求版本必须已经批准且当前有效。缺少门槛时停止，不得用草案继续设计。

## 工作方式

`sdlc_status.recommendedAction` 是本轮唯一工作分支，必须先判断，再装配上下文或写文档：

- `recommendedAction.target` 明确给出本轮唯一 `kind`、`scopeId` 和 `documentPaths`；普通候选必须逐项
  完全一致，并严格采用其中的 `parentVersionId`；值为 `null` 时必须省略候选参数。不得改写、重新提交
  或顺带包含已经批准的其他设计文档；

- 原因为“需要生成并审核总设计版本”时，只能调用一次
  `sdlc_set_candidate_create(kind=DESIGN_SET)`；不得装配上下文、不得写设计文档、不得调用普通候选工具；
- 原因为产品总体设计尚未批准时，只维护产品总体设计；
- 原因为某个模块设计或测试说明尚未批准时，只处理状态点名的模块，并且同步维护该模块的
  `design.md` 与 `verification-spec.md`；
- 原因为外部接口设计尚未批准时，只处理状态点名的接口；
- 状态存在待审核候选时只返回其审核命令，不得创建其他候选。

创建普通设计候选时，首个修订不得传 `parentVersionId`；只有修订既有批准版本时才传入当前
版本编号。需求版本属于设计输入，不是首个设计修订的父版本。

1. 使用 `sdlc_context_assemble` 装配当前模块最小上下文，不读取所有模块全文。
2. 产品总体设计只维护跨模块边界、运行、数据、信任、部署、失败恢复和系统测试原则。
3. 模块设计说明职责、接口、数据、状态、并发、错误、权限、实现路径、追溯、风险和替代方案。
4. 模块测试说明与设计同步维护，规定单元、模块集成、契约、必要界面测试、环境、通过条件和证据。
5. 模块设计候选必须同时包含 `design.md` 和 `verification-spec.md`，并结构化声明允许的产品路径和测试路径。
6. 外部接口设计描述协议、逻辑地址模板、认证、错误、兼容和契约测试；实际地址只进入环境版本。
7. 所有模块和接口设计批准后，使用 `sdlc_set_candidate_create` 生成精确总设计版本。

## 文档合同

模块设计候选的两个文件路径固定为：

- `docs/design/modules/<模块路径名>/design.md`
- `docs/verification/modules/<模块路径名>/verification-spec.md`

不得把 `verification-spec.md` 放到 `docs/design` 下，也不得创建同名副本。接口设计固定使用
`docs/design/interfaces/<接口路径名>.md`；产品总体设计固定使用
`docs/design/product-architecture.md`。总设计版本由工具生成，不手写重复汇总文档。

不得读取 `.sdlc-factory` 或 `.opencode` 内部文件，不得扫描无关子项目。禁止对项目根、
`node_modules` 或依赖目录使用 `glob("*")`、递归 glob 或目录遍历。需要目标脚手架事实时，
先读取根级 `package.json`，再按其中已经确认的入口读取少量精确文件；只读取当前项目明确相关的
配置、入口和目标模块路径，并在上下文记录纳入原因。已从最小上下文和精确入口取得路径事实后
立即停止扫描，不得为了“了解项目结构”枚举整个工作区。

候选校验使用以下必要章节名：

- 产品总体设计：系统边界、模块关系、运行、数据、认证、部署、失败、系统测试、设计决定；
- 模块设计：输入版本、模块目标、范围、接口、数据、状态、错误、权限、实现路径、追溯、风险、修订；
- 接口设计：输入版本、协议、地址、请求、响应、认证、超时、错误码、演进、契约测试。

不创建能力单元、执行计划或新的项目级任务层。形成候选后原样采用候选工具返回的唯一审核命令并停止，不得继续提问或进入编码。

## 1. 验收范围

本次验收检查当前插件重构是否真正满足以下合同：

- 不再使用能力单元、执行计划或独立项目计划；
- 从登记来源生成模块化需求产物；
- 候选固定文件字节、内容哈希和输入引用；
- 用户直接审核后生成不可变版本；
- 项目进度只从生命周期事实推导；
- 编码使用 OpenCode 原生待办；
- 测试命令等待真实进程退出，不使用固定 `sleep`；
- 模块测试、系统 Playwright 测试、测试记录和报告保持不同职责；
- 识别不必要的模型调用和上下文消耗。

所有类型检查、自动化测试、构建和差异检查均由 OpenCode CLI 调用。外层只按同一进程的输出和退出状态等待，没有使用固定时长判断成功。

## 4. 异常与修正

### 4.1 首次需求生成扫描过多

修补前会话除 `skill`、`sdlc_status` 和 `sdlc_source_read` 外，还使用了工作区 `glob`、多次 `grep`、重复读取技能、内部清单和无关子项目，最终还因章节不完整重复写入候选。该会话达到 12 个助手回合、6,347 个推理量和 156,672 个缓存读取量，明显异常。

修正包括：

- 需求 Skill 明确禁止重复读技能、全工作区扫描和读取插件内部状态；
- 插件钩子在需求阶段确定性阻止 `glob`、`grep` 和越界原生读取；
- 来源正文只能通过 `sdlc_source_read` 获取；
- 列出产品概述必需章节，候选形成后立即停止；
- 隔离父目录旧插件状态，避免 OpenCode 向上发现过期技能。

修正后的产品概述会话只调用状态、技能、登记来源、文档写入和候选工具，没有扫描工作区。相较首次异常会话，助手回合减半，推理量约下降 50%，缓存读取量约下降 75%。该会话曾被外层 60 秒命令上限中断展示，但候选写入已原子完成；后续改为持续跟踪同一进程退出，不据固定等待判断结果。

### 4.2 审核缺少候选详情投影

原 `/sdlc-review` 只能从状态获得候选编号和哈希，拿不到父版本、文件、检查和影响详情。模型因此尝试扫描 `.sdlc-factory`、`.opencode` 和工作区；内部读取被插件阻止，但仍浪费回合。Windows CLI 还会把带空格的单一引用参数保留首尾引号，严格审核解析正确拒绝了两次不完全匹配文本。

修正包括：

- 新增 `sdlc_candidate_read`，只返回安全、不可变的审核投影；
- 不返回内部快照路径和创建会话内部信息；
- `/sdlc-review` 只允许状态工具和候选投影工具，不再扫描或直接读文件；
- Windows CLI 验收使用多个无引号参数传递严格审核原文。

修补后只用 3 个助手回合完成候选投影与状态核对，`reasoning` 为 147，并确认没有 `snapshotPath`。

### 4.3 确定性测试的模型开销

自动化测试本身只需约 2 秒，但完整 OpenCode 会话还包含模型启动、工具选择和总结时间。把类型检查、测试、构建和差异检查放在一个会话内，以四次独立工具调用执行，可以摊薄每个独立会话的固定上下文成本。产品正常运行时，测试执行由受控执行器直接等待进程退出并记录证据，不应让模型重复生成测试或轮询日志。

### 4.4 大范围模型代码审查不适合作为常规门槛

一次要求模型审查整个插件差异的只读会话在 10 分钟外层上限前仍未形成结论。它读取了大量源码、测试、命令和生成包，累计 130,982 个输入、15,921 个推理量和 710,656 个缓存读取量。该会话已经超时，不能作为通过或失败证据。

这说明对大差异执行无边界模型审查会重现“大文档一次性进入模型”的同类问题。合理做法是：

- 确定性类型检查、测试、构建和路径检查作为固定门槛；
- 模型审查按候选、审核、命令执行、测试记录等单一风险链分开；
- 禁止读取生成包和无关目录；
- 每个审查会话限制文件清单和需要回答的问题；
- 超时且无结论的会话只记录异常，不伪装成审查通过。

人工沿该会话已读取的路径边界继续复核，发现原实现只做字符串路径判断，项目内目录链接可以指向项目外。现已改为校验目标或最近存在父目录的真实路径，并增加目录链接越界测试，防止文档写入、测试指纹和命令工作目录通过链接逃逸工作区。

## 5. 推理流程评估边界

不能也不应读取或披露模型隐藏思维链。本报告只审计可观察内容：用户输入、工具顺序、工具参数、退出状态、文档产物、候选、审核和用量统计。

修补后的可观察流程为：

```text
读取当前状态
→ 加载当前技能
→ 读取已登记来源
→ 区分事实与未知
→ 写入受控文档
→ 确定性校验并固定候选
→ 用户按编号和完整哈希直接审核
→ 生成不可变版本
→ 从事实推导下一门槛
```

该顺序与当前正式设计一致：AI 只生成草案和工具参数，系统校验结构与哈希，用户负责批准，状态不由 AI 自报。已发现的扫描、重复读取、缺少审核投影和 Windows 参数问题均已形成代码或规则修正。

## 6. 尚未完成的真实验收

自动化测试已经覆盖两个业务模块的完整生命周期状态重建，但仍需在真实产品脚手架完成：

1. 两个业务模块的实际编码和 OpenCode 原生待办留证；
2. 项目原生单元、模块集成和契约测试；
3. 完整应用启动与业务就绪检查；
4. 已存在 Playwright 代码的跨模块流程；
5. 系统测试记录、报告和系统验收审核。

因此当前结论是“插件核心合同实现并通过自动化与需求审核链验收”，不是“完整目标项目已经交付”。

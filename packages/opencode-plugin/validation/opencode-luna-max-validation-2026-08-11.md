## 1. 验收范围

本次验收检查当前插件重构是否真正满足以下合同：

- 不再使用能力单元、执行计划或独立项目计划；
- 从登记来源生成模块化需求产物；
- 候选固定文件字节、内容哈希和输入引用；
- 用户直接审核后生成不可变版本；
- 项目进度只从生命周期事实推导；
- 编码使用 OpenCode 原生待办；
- 测试命令等待真实进程退出，不使用固定 `sleep`；
- 模块测试、系统 Playwright 测试、测试记录和报告保持不同职责；
- 识别不必要的模型调用和上下文消耗。

所有类型检查、自动化测试、构建和差异检查均由 OpenCode CLI 调用。外层只按同一进程的输出和退出状态等待，没有使用固定时长判断成功。

## 4. 异常与修正

### 4.1 首次需求生成扫描过多

修补前会话除 `skill`、`sdlc_status` 和 `sdlc_source_read` 外，还使用了工作区 `glob`、多次 `grep`、重复读取技能、内部清单和无关子项目，最终还因章节不完整重复写入候选。该会话达到 12 个助手回合、6,347 个推理量和 156,672 个缓存读取量，明显异常。

修正包括：

- 需求 Skill 明确禁止重复读技能、全工作区扫描和读取插件内部状态；
- 插件钩子在需求阶段确定性阻止 `glob`、`grep` 和越界原生读取；
- 来源正文只能通过 `sdlc_source_read` 获取；
- 列出产品概述必需章节，候选形成后立即停止；
- 隔离父目录旧插件状态，避免 OpenCode 向上发现过期技能。

修正后的产品概述会话只调用状态、技能、登记来源、文档写入和候选工具，没有扫描工作区。相较首次异常会话，助手回合减半，推理量约下降 50%，缓存读取量约下降 75%。该会话曾被外层 60 秒命令上限中断展示，但候选写入已原子完成；后续改为持续跟踪同一进程退出，不据固定等待判断结果。

### 4.2 审核缺少候选详情投影

原 `/sdlc-review` 只能从状态获得候选编号和哈希，拿不到父版本、文件、检查和影响详情。模型因此尝试扫描 `.sdlc-factory`、`.opencode` 和工作区；内部读取被插件阻止，但仍浪费回合。Windows CLI 还会把带空格的单一引用参数保留首尾引号，严格审核解析正确拒绝了两次不完全匹配文本。

修正包括：

- 新增 `sdlc_candidate_read`，只返回安全、不可变的审核投影；
- 不返回内部快照路径和创建会话内部信息；
- `/sdlc-review` 只允许状态工具和候选投影工具，不再扫描或直接读文件；
- Windows CLI 验收使用多个无引号参数传递严格审核原文。

修补后只用 3 个助手回合完成候选投影与状态核对，`reasoning` 为 147，并确认没有 `snapshotPath`。

### 4.3 确定性测试的模型开销

自动化测试本身只需约 2 秒，但完整 OpenCode 会话还包含模型启动、工具选择和总结时间。把类型检查、测试、构建和差异检查放在一个会话内，以四次独立工具调用执行，可以摊薄每个独立会话的固定上下文成本。产品正常运行时，测试执行由受控执行器直接等待进程退出并记录证据，不应让模型重复生成测试或轮询日志。

### 4.4 大范围模型代码审查不适合作为常规门槛

一次要求模型审查整个插件差异的只读会话在 10 分钟外层上限前仍未形成结论。它读取了大量源码、测试、命令和生成包，累计 130,982 个输入、15,921 个推理量和 710,656 个缓存读取量。该会话已经超时，不能作为通过或失败证据。

这说明对大差异执行无边界模型审查会重现“大文档一次性进入模型”的同类问题。合理做法是：

- 确定性类型检查、测试、构建和路径检查作为固定门槛；
- 模型审查按候选、审核、命令执行、测试记录等单一风险链分开；
- 禁止读取生成包和无关目录；
- 每个审查会话限制文件清单和需要回答的问题；
- 超时且无结论的会话只记录异常，不伪装成审查通过。

人工沿该会话已读取的路径边界继续复核，发现原实现只做字符串路径判断，项目内目录链接可以指向项目外。现已改为校验目标或最近存在父目录的真实路径，并增加目录链接越界测试，防止文档写入、测试指纹和命令工作目录通过链接逃逸工作区。

### 4.5 系统验收错误地让模型重构历史测试参数

系统测试版本批准后，旧流程仍让模型调用 `sdlc_test_reuse_find`，重新猜测原运行的命令顺序、工作目录和 33 个指纹文件。虽然没有重跑测试，但会话持续 746.1 秒，累计 89,407 个输入、17,560 个推理量和 1,671,168 个缓存读取量；期间产生大量不匹配查询，并一度把 Playwright 源码重复放入系统验收候选。

修正包括：

- 新增 `sdlc_system_acceptance_candidate_create` 专用工具；
- 只允许它创建系统验收候选，通用候选入口不能绕过；
- 工具内部读取当前有效系统测试版本，精确复用同一报告和同一批测试记录；
- 系统验收输入只包含当前系统测试版本，候选只包含自动报告；
- 报告当前字节与已批准系统测试版本不一致时拒绝创建；
- Skill 明确禁止在该阶段启动运行、调用复用查询或读取测试正文。

修补后的真实会话只调用 Skill、状态和专用工具，18.6 秒形成正确候选；输入降至 20,728，推理量降至 184，缓存读取降至 15,360。修补前候选被正式退回，修补后候选经审核形成 `system-acceptance-system-r1`。

### 4.6 项目进度没有主动识别工作区代码漂移

原状态只校验版本之间的引用关系。若用户或外部工具直接修改已批准代码，下一次运行会在门槛处拒绝，但 `/sdlc-status` 仍可能显示旧代码和系统验收有效，这与“项目级最新状态”的定义冲突。

现已在每次状态查询中校验已批准代码字节以及测试记录中的代码、测试代码和工具链指纹。独立迁移副本首先恢复为“已验收”；修改系统管理的一处已批准代码后，系统管理和依赖它的审计管理同时变为 `CODING / INVALIDATED`，系统测试与系统验收版本不再有效，唯一建议变为 `/sdlc-code 系统管理`。随后执行 `/sdlc-test system` 只返回前置失效原因，未执行命令或生成记录。

## 5. 推理流程评估边界

不能也不应读取或披露模型隐藏思维链。本报告只审计可观察内容：用户输入、工具顺序、工具参数、退出状态、文档产物、候选、审核和用量统计。

修补后的可观察流程为：

```text
读取当前状态
→ 加载当前技能
→ 读取已登记来源
→ 区分事实与未知
→ 写入受控文档
→ 确定性校验并固定候选
→ 用户按编号和完整哈希直接审核
→ 生成不可变版本
→ 从事实推导下一门槛
```

该顺序与当前正式设计一致：AI 只生成草案和工具参数，系统校验结构与哈希，用户负责批准，状态不由 AI 自报。已发现的扫描、重复读取、缺少审核投影和 Windows 参数问题均已形成代码或规则修正。

## 6. 完整目标项目验收与方案结论

真实目标项目从原始需求走通了全部插件阶段：需求分析与修订、一级业务模块拆分、外部接口和非功能需求、总体与模块设计、测试说明、两个模块编码和原生待办、模块测试、完整应用启动、Playwright 跨模块系统测试、自动报告、系统测试审核和系统验收审核。不存在用自动化状态重建替代实际编码或测试的情况。

需求和设计产物规模如下：

| 产物 | 大小 | 结论 |
| --- | ---: | --- |
| 产品概述 | 3.3 KB | 只保存范围、角色、模块和未知，适合作为入口 |
| 需求地图 | 1.6 KB | 只保存一级模块、依赖、接口和非功能需求索引，适合作为“大地图” |
| 系统管理需求 | 7.5 KB | 当前最大需求文件，仍低于单次最小上下文上限 |
| 审计管理需求 | 3.7 KB | 模块边界清晰 |
| 外部接口需求 | 3.5 KB | 与实际环境地址分离合理 |
| 全局非功能需求 | 3.2 KB | 独立版本化且由模块引用合理 |
| 产品总体设计 | 6.4 KB | 只描述跨模块结构和系统测试边界 |
| 两个模块设计 | 5.2 KB、4.3 KB | 与各自测试说明及代码路径边界绑定合理 |
| 两份模块测试说明 | 3.8 KB、3.0 KB | 在编码前固定测试责任合理 |
| 系统测试报告 | 2.8 KB | 由结构化记录自动生成，适合作为人工审核投影 |

方案评估结论：

- 不再引入能力单元或独立项目计划是合理的；一级业务模块同时作为需求、设计、编码和测试的稳定边界，避免多套拆分语义冲突。
- 产品概述、需求地图、模块需求、接口需求、非功能需求和总需求清单的拆分合理；“大地图”保存最新结构和版本引用，历史由候选、审核和不可变版本保存。
- 设计沿用同一业务模块边界，但不机械复制需求目录；产品总体设计负责跨模块决策，模块设计与测试说明成包，接口设计单独版本化，粒度合理。
- 测试说明、版本化测试代码、结构化测试记录和自动报告四者都有必要，职责不同；Playwright 只负责完整应用跨模块流程，不能替代模块原生测试。
- 项目进度作为只读实时投影合理，不应另存一份 Todo 或计划；编码过程继续使用 OpenCode 原生待办，两者没有事实冲突。
- 系统测试和系统验收保留两个审核版本合理，但测试只执行一次；专用确定性入口消除了重复模型推理和候选内容歧义。

当前插件产品的验收条件已经满足。仍需持续回归的场景是未来真实需求变化时的模块拆分、合并、退役和多环境切换；它们属于版本演进，不是本次插件交付缺口。

## 7. 最终产品复核

2026-08-13 以插件为唯一产品形态重新审视运行目录、文档体系和模型消耗，得到以下结论：

- 最终代码回归为 19 个测试文件、55 项测试，类型检查和构建通过；新增覆盖内容寻址字节复用、模块测试专用候选、系统测试专用候选和零模型状态入口。
- 产品文档按产品概述、需求地图、模块需求、接口需求、非功能需求和总需求版本拆分合理；它们分别承担公共范围、导航、模块行为和组合版本职责，没有形成第二份巨型需求报告。
- 开发文档按产品总体设计、模块设计、接口设计、同步测试说明和总设计版本拆分合理；设计与需求使用同一业务模块，编码路径和测试路径在批准前固定。
- 测试说明、测试代码、结构化测试记录和自动报告必须继续分离；Playwright 只负责跨模块完整流程，不能替代原生模块测试。
- 完整验收项目的 `.sdlc-factory` 包含 145 个 JSON、1 个追加式事件文件和 72 个候选快照，总计约 512 KB。每个 JSON 对应一条候选、审核、版本、运行、命令证据、测试记录、来源或环境事实，数量合理；把它们合并为可变大文件会破坏单条不可变性和损坏隔离。
- 原快照中约 57 KB 是相同字节重复。新实现将候选字节保存到 `objects/sha256` 并按哈希复用；模块测试候选不再重复快照已由代码版本固定的测试代码。
- 新增 `sdlc_module_test_candidate_create` 和 `sdlc_system_test_candidate_create`。两个工具分别从通过测试记录恢复运行、版本和 Git 基点，减少模型重构参数；系统验收继续使用原有专用入口。
- 模型消耗的主要风险不是隐藏 JSON 数量，而是无边界扫描、重复读 Skill、大范围代码审查和让模型重构确定性事实。来源读取上限、最小上下文上限和三个测试候选专用入口已经覆盖这些风险。
- 交互式 `/sdlc-status` 在隔离副本中实测 19.9 秒，合计输入 9069、输出 50、推理 569、缓存读取 7680；人工偶发使用可以接受，自动化轮询不合理。新增 `node .opencode/bin/sdlc-status.mjs` 后，同一副本可在不启动模型的情况下恢复“已验收”、两个模块完成以及当前精确版本。
- 真实旧验收项目重新执行时，历史 `revisions/` 内的 `.test.ts` 快照会被未配置排除规则的 Vitest 误收集；显式排除 `.sdlc-factory/**` 后，10 个测试文件、30 项测试全部通过，完整应用打包通过。当前内容寻址对象没有扩展名，新流程不会再产生该污染；旧状态必须保留审核历史并按兼容策略处理，不能静默删除。
- 该旧目标的 `verify:template` 仍引用已不存在的 `.sdlc-pipeline/contracts/scaffold.json`，因此组合脚本不作为当前插件通过证据。有效的代码检查、类型检查、排除状态目录后的项目测试和打包已分别通过；该遗留脚本属于被研发项目自身的历史问题，不属于 Factory 产品形态。

正式判断与运行目录规范见 [DESIGN-04《插件产物与质量设计》](../../../docs/design/04-plugin-artifact-quality-design.md)。

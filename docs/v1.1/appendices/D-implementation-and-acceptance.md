# 附录 D：实施与验收

## 1. 实施策略

1.1 按可独立验收的纵向切片实施。每一步先建立合同和黑盒测试，再替换当前插件行为。
不要在旧的特殊重试、聊天 JSON 解析和角色目录门禁上继续叠加兼容分支。

## 2. 第 0 阶段：冻结合同

交付：

- 1.1 领域词汇和英文编码名；
- 专业编排包、Core、观察适配器、执行器和产物检查器的端口；
- 交付证据与运行遥测的独立模型；
- 不兼容变更清单；
- 架构依赖测试。

验收：

- OpenCode 专属类型不进入 Core 领域对象；
- Agent、Skill 和 Hook 不拥有状态转换；
- JSON 索引不保存会话或报告正文；
- 1.0 正式产物的迁移或明确废弃策略已决定。

## 3. 第 1 阶段：先修复确定性缺陷

交付：

- 宿主在模型前保存原始需求字节和哈希；
- `sdlc_handoff_submit`；
- 测试结果四态；
- 新反馈优先于旧复验计划；
- 检查范围、交付目标和实际 diff 分离；
- 删除角色目录 ACL，保留全局保护规则。

黑盒场景：

1. 输入包含中文弯引号，`input.md` 字节和哈希保持一致；
2. `/sdlc-test` 收到新的 `test_issue` 后，不先重复旧 `reverify_test`；
3. Agent 聊天前后包含说明文字，结构化交接仍可独立成功；
4. Tester 可读取实现文件并修改声明的测试文件；
5. 未声明 diff 被审计，但不会因隐式角色 ACL 产生矛盾错误；
6. 必测脚本输出 `SKIP` 且进程退出 0，门禁仍不通过；
7. `blocked`、`failed`、`skipped` 在聚合结果中保持原状态。

## 4. 第 2 阶段：建立运行观察

交付：

- 宿主观察适配器端口；
- OpenCode 首个适配器；
- 运行、会话、子代理、阶段和操作关联；
- 标准事件和原始事件保留；
- Token、成本、工具和耗时字段规范化；
- Secret 脱敏。

验收：

- 使用伪造事件流可以完整测试，不要求启动 OpenCode；
- 缺少某个提供方字段时标记 `unavailable`，不补造零值；
- 取消的会话记录为未完成，不被统计为成功路径；
- 父会话等待子代理的时间不与子代理耗时重复相加；
- 原始提示词、设备密码和认证头不进入遥测。

## 5. 第 3 阶段：建立独立运行分析

交付：

- 阶段耗时、工具调用、Token 和成本汇总；
- 实际总量、成功路径和返工开销；
- 重复读取、相同失败和无进展分析；
- 同类工作项基线；
- 中文运行分析报告；
- `sdlc_analysis_get` 查询工具。

黑盒场景：

1. 同一路径在同一有效上下文重复读取被识别；
2. 不同 Agent 首次读取同一路径不被误判为同会话重复；
3. 重试导致的上下文重建单独统计；
4. 相同输入、相同错误连续执行被识别为无新增信息重试；
5. 一次生成打满 reasoning token，但有有效产出时只报告异常值，不判失败；
6. OpenCode `cost=0` 且没有提供方账单时报告“OpenCode 估算为 0，实际结算未知”；
7. 被取消和失败运行只进入实际总量及返工开销；
8. 墙钟时间、模型时间、工具时间和人工等待可分别解释；
9. 报告可在没有 Codex 监督的情况下由插件独立生成。

## 6. 第 4 阶段：建立产物符合性检查

交付：

- 需求覆盖矩阵；
- 正式输入和证据哈希绑定；
- UI、协议、架构、安全专业验收 Agent；
- 必测状态和证据新鲜度门禁；
- 中文产物验收报告。

黑盒场景：

1. 代码存在但没有需求覆盖证据时结果为 `uncertain`；
2. UI 截图与指定原型明显不一致时不能通过；
3. 设置按钮无响应时对应验收条件为 `unsatisfied`；
4. 协议要求鉴权但实现直接调用业务接口时不能通过；
5. 错误密码、Token 失效和网络错误缺少用户反馈时不能通过；
6. 测试证据属于旧源码修订时自动失效；
7. 真实设备必测项被跳过时阻止交付；
8. 日志或报告出现明文凭据时阻止交付；
9. 专业 Agent 无法确定 TLS 信任方式时输出 `uncertain`，不自行假设。

## 7. 第 5 阶段：接入专业编排包

交付：

- Agent、Skill、Hook 和规则注册表；
- 稳定负责人和按需专家；
- 两层委派；
- 结构化失败分类与责任路由；
- 专业能力版本和内容哈希。

验收：

- 小工作项不启动无关专家；
- 跨领域工作项只启动命中的专家；
- 上一阶段产物以引用传递，不复制整个会话；
- Coder 不需要为了获得项目读写权限绕回主会话；
- Tester 保持独立上下文，可检查实现并提交测试修改；
- 专家结果未变化时可以复用，正式输入变化时自动失效；
- Hook 关闭后，Core 状态机仍可通过 CLI 驱动。

## 8. 第 6 阶段：真实项目对照

选择至少三个项目：

- 单模块、无外部设备；
- 多模块或 Electron；
- 具有真实设备、鉴权和高保真 UI。

每个项目运行：

```text
init → spec → code → human review → test → delivery preview
```

至少注入：

- 一次实现问题；
- 一次测试实现问题；
- 一次需求问题；
- 一次环境阻塞；
- 一次 Agent 交接错误；
- 一次插件工具错误；
- 一次取消后重试。

对照指标：

- 阶段墙钟时间；
- 模型、工具、Core 和人工等待时间；
- 各角色 input/output/reasoning token；
- 实际总量、成功路径和返工开销；
- 工具成功率和重复调用；
- 错误责任分类准确率；
- 需求覆盖和最终产物结论；
- 是否仍需 Codex 手工拼接日志和成本。

## 9. 停止条件

测试过程中出现以下任一情况应暂停并形成故障报告，不无限重试：

- 同一失败指纹连续出现三次且没有新增诊断；
- Core 状态与正式 Markdown 产物不一致；
- Secret 进入日志、状态或 Git；
- 工作流在无 Operator 决定时越过审批；
- 必测项被 `skip` 或 `blocked` 误判通过；
- 观察适配器改变了工作流真相；
- 测试环境或设备状态无法确认，继续运行会产生误导结论。

## 10. 1.1 完成定义

只有同时满足以下条件才可宣布 1.1 可用：

- 所有确定性黑盒场景通过；
- 完整回归通过；
- 三类真实项目对照完成；
- 运行分析报告由插件独立生成；
- 最终产物验收报告由插件独立生成；
- 报告能解释阶段耗时、Token、成本可用性、工具异常和返工来源；
- 报告结论与正式需求、源码修订和证据一致；
- 无需 Codex 手工读取 OpenCode 日志才能判断插件是否发生调用爆炸；
- Operator 仍保留需求、人工审核和交付批准权。

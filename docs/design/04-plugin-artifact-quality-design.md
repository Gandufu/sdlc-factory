## 1. 产品边界

SDLC Factory 的最终产品形态是安装到目标项目中的 OpenCode 生命周期插件。产品范围从原始资料登记开始，覆盖需求、设计、编码、模块测试、系统测试、人工审核和系统验收，不包含独立图形客户端、独立服务端、项目门户或通用工作流引擎。

插件对用户公开的是 `/sdlc-*` 命令、用户可读文档、候选审核和项目进度。隐藏目录中的结构化文件是插件事实，不是要求用户阅读的文档，也不得整体送入模型上下文。

## 2. 产品角度的需求产物

需求文档采用以下分层：

| 产物 | 回答的问题 | 不承担的职责 |
| --- | --- | --- |
| 产品概述 | 为什么建设、服务谁、范围和明确排除项是什么 | 不复制模块详细需求 |
| 需求地图 | 有哪些一级业务模块、依赖、接口和质量约束 | 不保存视觉布局状态和完整历史 |
| 模块功能需求 | 一个业务模块需要产生哪些可观察行为 | 不写实现方案和实际环境地址 |
| 外部接口需求 | 需要什么外部能力、输入输出和业务错误 | 不写测试环境的真实地址和凭据 |
| 非功能需求 | 性能、安全、可靠性等目标及验证方法 | 不写无法验证的宣传性描述 |
| 总需求版本 | 当前全部已批准需求的精确组合 | 不复制正文，不使用“最新”引用 |

该拆分合理，因为它同时满足完整产品范围、一级业务模块的最小上下文和跨模块追溯。需求条目必须有稳定编号、来源、可观察结果和验证方法；无法确认的内容保留为未知。业务模块拆分、合并或退役必须先修改需求地图并经用户审核。

## 3. 开发角度的设计产物

设计文档采用以下分层：

| 产物 | 主要内容 | 编码输入关系 |
| --- | --- | --- |
| 产品总体设计 | 跨模块结构、运行、数据、安全、部署和系统测试原则 | 绑定总需求版本 |
| 模块设计 | 职责、接口、数据、状态、错误、权限和实现路径边界 | 绑定模块需求和总需求版本 |
| 接口设计 | 协议、路径、认证、超时、重试、错误码和演进 | 绑定接口需求和总需求版本 |
| 模块测试说明 | 编码前明确验证目标、范围、环境和通过条件 | 与模块设计作为同一候选审核 |
| 总设计版本 | 当前总体、模块和接口设计的精确组合 | 是编码和测试的共同门槛 |

设计沿用需求阶段的业务模块，不再创造平行执行单位。测试说明与模块设计同步批准是必要的，因为测试责任必须在编码前明确；低层断言和测试数据以版本化测试代码为准，不在 Markdown 中复制成庞大测试用例手册。

代码版本同时固定产品代码和测试代码。模块测试版本只引用通过的测试记录以及其输入代码版本，不再次复制测试源文件。系统测试版本只固定自动报告和系统测试记录。系统验收只引用已批准系统测试版本、同一报告和同一批记录，不重新执行测试。

## 4. 测试角度的产物

测试相关产物分成四层：

1. 测试说明：设计阶段确定需要验证什么；
2. 测试代码：编码阶段维护并进入代码版本；
3. 测试记录：一次确定性执行的输入版本、环境、命令、结果和文件指纹；
4. 测试报告：从测试记录生成的人工审核投影。

四者不能合并。测试说明不能代替可执行测试，测试代码不能证明已经运行，测试报告不能脱离底层记录声称通过。模块测试使用项目原生执行器；Playwright 只负责完整应用的跨模块关键流程。

模块测试和系统测试候选通过专用工具生成。模型只需要提供刚形成的测试记录编号，工具自行恢复运行、输入版本、Git 基点和固定产物，避免模型重复拼装版本清单、测试路径和文件指纹。

## 5. 运行目录与结构化事实

目标项目中的隐藏状态采用“一条不可变事实一个 JSON 文件”，目录职责如下：

| 目录或文件 | 保存内容 | 是否可删除或合并 |
| --- | --- | --- |
| `manifest.json` | 项目身份、插件版本和授权边界 | 项目存在期间保留 |
| `sources/` | 原始资料索引和哈希 | 保留 |
| `source-snapshots/` | 初始化时固定的原始资料字节 | 保留 |
| `objects/sha256/` | 候选正文和代码的按哈希复用快照 | 相同内容只保存一次 |
| `candidates/` | 候选范围、输入、文件、哈希和影响 | 退回候选也保留 |
| `reviews/` | 用户通过、退回或暂缓决定 | 保留 |
| `approved-versions/` | 已批准版本的自包含事实 | 保留，不能只存易断裂的指针 |
| `runs/` | 编码和测试运行的固定输入及权限范围 | 保留 |
| `command-evidence/` | 每条受控命令的退出码、耗时和日志索引 | 保留 |
| `test-runs/` | 测试结论、环境、文件指纹和证据索引 | 保留 |
| `environments/` | 实际地址、依赖版本和凭据引用 | 保留 |
| `journal.jsonl` | 追加式事件，用于恢复运行和待办状态 | 保留，不直接暴露给模型 |
| `evidence/` | 完整标准输出、错误输出、截图、视频和跟踪文件 | 按项目证据策略归档 |

JSON 数量不是质量指标。将候选、审核、运行和测试记录合并成少数可变大文件，会增加并发覆盖、局部损坏、写入中断和审计断链风险。合理性应按以下指标判断：

- 每个文件是否代表单一事实；
- 是否存在无法追溯来源的投影；
- 相同正文是否按内容哈希复用；
- 日志和二进制证据是否与结构化状态分离；
- 状态查询是否只返回必要投影，而不是原始 JSON；
- 模型是否被禁止扫描隐藏目录。

现有完整验收项目在优化前包含 145 个 JSON、1 个追加式事件文件和 72 个候选快照，总隐藏状态约 512 KB。JSON 分布对应 24 个候选、24 个审核、19 个批准版本、12 个运行、58 条命令证据、4 条测试记录、2 个来源和1个环境，均能解释其业务来源。问题不在 JSON 数量，而在约 57 KB 相同候选字节被重复快照；新实现通过 `objects/sha256` 内容寻址和测试专用候选入口消除后续重复。

旧版 `revisions/` 曾按源文件名保存快照，其中 `.test.ts`、`.test.tsx` 可能被未排除隐藏目录的测试执行器误识别。新候选统一保存为无扩展名的哈希对象，已经从结构上消除该问题。升级安装器会先校验所有被引用旧快照的字节大小和 SHA-256，再将全部旧文件写入内容对象，保存 `migrations/revisions-to-objects-v1.json` 路径映射清单，最后删除旧目录。候选与已批准版本文件保持逐字节不变；读取器在旧路径不存在时通过清单定位内容对象。校验失败时拒绝迁移并保留旧状态。

当前规模不需要数据库或压缩归档。只有单项目结构化状态达到 100 MB 或不可变事实超过 10000 条时，才应设计带清单、哈希和恢复测试的冷归档；不得以定期清理方式删除审核历史。

## 6. 模型调用与 token 约束

模型只用于读取业务资料、分析语义、生成需求与设计草案、编码和解释问题。以下工作必须由确定性工具完成：

- 计算哈希、版本号和当前状态；
- 组合总需求和总设计版本；
- 执行命令、记录退出码和保存日志；
- 比较文件指纹和判断证据是否可复用；
- 从测试记录生成报告；
- 从通过记录生成模块测试、系统测试和系统验收候选。

交互式 `/sdlc-status` 仍会经过一次 OpenCode 模型回合。自动化、持续集成和频繁监控必须改用目标项目中的 `node .opencode/bin/sdlc-status.mjs`；该入口调用同一状态服务并直接输出结构化事实，不产生模型 token。

来源单次最多读取 12000 个字符；最小上下文默认 30000 个字符、硬上限 60000 个字符；单个正文最多装配 12000 个字符。代码版本只向模型提供路径、哈希和必要源文件读取，不把所有代码快照作为结构化状态展开。

token 合理性不能只看一次会话总数，应同时检查助手回合、缓存读取、工具调用和是否得到有效产物。以下情况判定为浪费：

- 扫描整个工作区或隐藏状态目录；
- 重复读取已经返回完整内容的 Skill；
- 为确定性测试单独启动多个模型会话；
- 系统验收阶段重新推导历史命令和文件指纹；
- 没有明确问题边界的大范围模型代码审查；
- 测试等待期间轮询或把完整日志反复送入模型。

完整验收已证明：异常产品概述会话在约束后，助手回合减半、推理量约下降 50%、缓存读取约下降 75%；系统验收使用专用工具后由 746.1 秒降至 18.6 秒，推理量由 17560 降至 184。模块测试和系统测试现也使用专用候选入口，进一步消除版本清单和文件指纹的模型重构。

一次正常交互式状态查询实测约 19.9 秒，输入 9069、输出 50、推理 569、缓存读取 7680，适合人工偶发查询，但不适合持续轮询。零模型入口在同一隔离项目中直接恢复“已验收”及两个已完成模块，不产生模型调用，是自动化读取进度的正式入口。

## 7. 完成判定

插件只有同时满足以下条件才算完成：

1. 产品、接口和非功能需求能够分模块建立、修订和审核；
2. 设计、测试说明和实现路径能够绑定精确需求版本；
3. 两个存在依赖关系的真实模块完成编码和原生测试；
4. 完整应用通过外部接口检查和 Playwright 跨模块流程；
5. 系统测试和系统验收分别形成已批准版本，但测试只执行一次；
6. 重启后可以从项目事实恢复当前状态；
7. 代码、测试代码、环境或工具链漂移会使相关证据失效；
8. 自动化测试、类型检查、构建、安装和文档检查全部通过；
9. 用户文档能够说明安装、命令、产物、审核和故障边界；
10. 正式文档中不存在另一个产品形态或废弃领域模型。

现有真实目标项目已经满足前七项。本次收敛负责完成后续代码回归、安装验证、文档清理和最终交付检查。

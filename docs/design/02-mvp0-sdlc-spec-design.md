# `/sdlc-spec` 模块化需求设计

文档编号：DESIGN-02
状态：正式方案，当前插件实现已覆盖
更新日期：2026-08-13

上位设计：[DESIGN-01《OpenCode 生命周期插件总体设计》](./01-mvp0-opencode-plugin-design.md)

## 1. 目标

`/sdlc-spec` 是一个以真实资料为依据、可以多轮继续和中断恢复的需求论证过程。它不再维护一份不断膨胀的需求文档，而是维护由产品概述、需求地图、模块需求、外部接口需求和非功能需求组成的需求集合。

主要目标：

- AI 提问前实际读取相关资料和项目事实；
- 先确认完整产品范围，再拆分一级业务模块；
- 每次只处理一个业务模块或一类跨模块需求；
- 同一业务模块使用稳定编号贯穿后续设计、编码和测试；
- 外部接口和非功能需求独立维护，通过作用范围关联模块；
- 模块可以独立审核和形成已批准版本；
- 总需求版本精确组合各模块版本；
- 每次修订保留原因、来源、差异和影响；
- AI 上下文只包含当前工作需要的最小内容。

## 2. 权威关系

需求事实按以下顺序解释：

1. 原始资料；
2. 用户明确决定；
3. 已批准需求版本；
4. 工作草案；
5. 对话摘要和 AI 推断。

低层内容不能覆盖高层内容。AI 推断必须保持为待确认或未知，不能因为“合理”就变成需求事实。

## 3. 需求层级

### 3.1 固定层级

```text
产品
└─ 业务模块：系统管理
   ├─ 功能组：用户管理
   │  ├─ 功能：创建用户
   │  ├─ 功能：禁用用户
   │  └─ 需求条目
   ├─ 功能组：角色权限
   └─ 功能组：系统配置
```

### 3.2 拆分规则

业务模块是需求、设计、编码和测试共同使用的工作单位。首版按一级业务域拆分，例如“系统管理”，不按页面、技术层、数据库表或开发步骤拆分。

业务模块应满足：

- 有明确且用户可理解的业务目标；
- 范围内功能内聚；
- 与同级模块粒度相近；
- 依赖、接口和非功能约束可以明确；
- 可以独立形成需求、设计、代码和测试结果；
- 拆分后仍是有意义的业务范围，而不是技术碎片。

“用户管理”默认是“系统管理”内的功能组。只有系统管理本身已经大到无法独立设计、编码或测试时，Skill 才提出两个或三个拆分候选，并由用户决定是否把用户管理提升为独立业务模块。

### 3.3 不再使用的层级

本方案不再使用能力候选、能力单元或其他设计阶段派生执行单位。功能组不会因为技术上可以单独编码就自动成为业务模块。

## 4. 需求产物

目标项目采用以下结构：

```text
docs/requirements/
├─ product-brief.md
├─ requirement-map.md
├─ modules/
│  ├─ system-management/
│  │  └─ functional-requirements.md
│  └─ <module>/
│     └─ functional-requirements.md
├─ interfaces/
│  └─ <interface>.md
├─ quality/
│  ├─ global.md
│  └─ <module>.md
└─ requirement-set.yaml
```

### 4.1 产品概述

`product-brief.md` 保持简短，包含：

- 产品目标和价值；
- 系统边界和明确排除项；
- 主要角色和外部参与者；
- 运行环境和已确认技术约束；
- 产品原则；
- 顶层业务模块摘要；
- 全局假设、未知和开放问题；
- 当前总需求版本引用。

它是所有需求工作的公共入口，不复制各模块详细需求。

### 4.2 需求地图

`requirement-map.md` 是用户可读投影，展示：

- 业务模块及功能组摘要；
- 模块之间的执行依赖；
- 外部接口引用；
- 全局和模块非功能需求作用范围；
- 当前需求版本和状态；
- 变更影响和阻塞项。

地图布局、颜色和折叠状态不属于需求语义。结构化需求集合才是版本权威，地图正文必须由结构化事实生成或校验。

### 4.3 模块功能需求

每个业务模块维护一份 `functional-requirements.md`，至少包含：

1. 模块目标；
2. 包含和不包含范围；
3. 角色和权限；
4. 功能组与功能；
5. 原子需求条目；
6. 状态、异常、恢复和边界条件；
7. 依赖模块；
8. 外部接口引用；
9. 适用非功能需求引用；
10. 验证方法和验收要点；
11. 来源、假设、未知和开放问题；
12. 修订摘要。

### 4.4 外部接口需求

外部接口按外部系统、设备或协议合同拆分。需求文件只描述：

- 接口对象和业务用途；
- 必须支持的业务能力；
- 输入、输出和错误语义；
- 认证、授权和信任要求；
- 超时、可用性和恢复要求；
- 数据敏感性和保留要求；
- 适用业务模块；
- 来源和验证方法。

实际地址、端口、测试账号和明文凭据不进入需求文件。

### 4.5 非功能需求

非功能需求分为全局文件和模块文件，覆盖：

- 性能和时序；
- 安全、隐私和凭据；
- 可用性、可靠性和恢复；
- 兼容性和可移植性；
- 可维护性和可测试性；
- 可访问性和易用性；
- 部署、资源和环境限制。

每条非功能需求必须包含稳定编号、作用范围、目标或明确未知、验证方法和来源。AI 不得使用“行业默认”编造阈值。

## 5. 公开命令和工作焦点

公开入口只保留 `/sdlc-spec [业务模块名称]`。

未提供模块名称时，Skill 根据状态执行以下之一：

- 建立或补充产品概述；
- 建立或调整需求地图；
- 提出下一个应处理的业务模块；
- 补齐跨模块接口或非功能需求；
- 执行全局一致性检查；
- 推荐审核当前候选。

提供模块名称时，只处理该模块及其必要引用。命令不会自动进入设计、编码或测试。

## 6. 需求论证流程

### 步骤 0：恢复状态

调用项目状态工具并读取：

- 产品概述和需求地图；
- 当前业务模块及版本；
- 登记来源和来源哈希；
- 待审核候选；
- 修订记录；
- 当前开放问题；
- 已失效和受影响范围。

如果候选存在且文件没有变化，停止写作并推荐 `/sdlc-review`。如果文件已经变化，说明旧候选与工作草案不同，只能继续形成新候选。

### 步骤 1：资料取证

Skill 读取与当前产品或模块相关的来源，并把重要陈述分类为：

- 来源事实；
- 用户决定；
- 待确认推断；
- 开放问题；
- 缺少证据的未知。

资料取证进入结构化来源记录和相应需求文档，不额外生成第二份“需求分析报告”。

### 步骤 2：产品概述

AI 先形成完整产品概述，不直接跳到某个页面或功能。产品概述至少回答：

- 目标系统是什么；
- 用户和外部参与者是谁；
- 解决什么问题；
- 范围包含和排除什么；
- 已知运行环境和技术约束是什么；
- 哪些信息仍然未知。

### 步骤 3：需求地图

在进入详细功能前，先建立同层级业务模块。AI 必须展示父子树和依赖，识别：

- 只是功能组却被误当作业务模块的项目；
- 粒度明显不一致的模块；
- 只有技术名称、没有业务目标的模块；
- 跨模块流程被误写成独立模块；
- 外部接口或非功能需求被误写成可执行模块。

存在重大歧义时，每轮只提出一个最影响范围和结构的问题，并给出有限候选和推荐理由。

### 步骤 4：模块循环

每次只处理一个业务模块：

```text
读取上下文
→ 检查已有事实
→ 识别冲突和未知
→ 提出一个关键问题
→ 给出候选和影响
→ 用户决定
→ 更新模块需求
→ 检查完成条件
```

问题优先级为：

1. 模块范围；
2. 角色和权限；
3. 公共行为；
4. 数据和状态；
5. 错误和恢复；
6. 外部接口；
7. 验收和非功能要求。

### 步骤 5：需求条目

每条需求条目必须：

- 使用稳定编号；
- 只表达一个主要可观察结果；
- 指明所属业务模块和功能组；
- 区分前置条件、行为、失败和恢复；
- 关联来源；
- 说明验证方法；
- 不包含未经确认的实现方案。

若一句话包含多个可以独立失败或验收的行为，应拆成多条需求。

### 步骤 6：跨模块需求

模块逐个成立不代表系统整体成立。候选前至少走查：

- 身份认证和授权；
- 跨模块数据流；
- 关键状态同步；
- 外部系统失败和恢复；
- 全局安全、性能和可靠性要求；
- 三到五个最重要的端到端业务场景。

走查只加载涉及的模块、接口和非功能需求，不加载全部正文。

### 步骤 7：确定性检查

插件检查：

- 文件清单和路径；
- 稳定编号唯一性；
- 业务模块和功能组父子关系；
- 依赖引用是否存在；
- 接口和非功能需求作用范围；
- 来源引用和来源哈希；
- 需求地图与结构化事实一致性；
- 未知是否被误写成确定事实；
- 是否存在孤儿需求、孤儿接口或循环执行依赖。

### 步骤 8：独立预审

预审优先使用新的 OpenCode 会话。审查上下文包含：

- 当前模块需求；
- 产品概述；
- 地图中的目标节点和直接关系；
- 相关接口和非功能需求；
- 相关来源；
- 确定性检查结果。

审查不继承完整写作对话。结果为通过、存在关注项或不通过。关注项必须具体到文件、需求编号和修复建议。

### 步骤 9：候选和审核

创建模块需求候选前重新读取实际文件并验证：

- 模块目标、范围和功能组完整；
- 需求条目有来源和验证方法；
- 接口和非功能需求引用有效；
- 未知和开放问题明确；
- 预审结果存在；
- 文件内容和来源哈希匹配。

候选创建后停止 `/sdlc-spec`，输出候选编号、SHA-256、变更摘要、关注项和唯一建议 `/sdlc-review`。

## 7. 最小上下文装配

### 7.1 模块需求上下文

处理指定业务模块时装配：

```text
产品概述
+ 需求地图目标节点
+ 当前模块功能需求
+ 相关外部接口需求
+ 全局和模块非功能需求
+ 直接上下游模块摘要
+ 相关来源片段
+ 当前版本和开放问题
```

不装配其他模块完整正文、全部历史版本或完整会话。

### 7.2 跨模块审查上下文

先装配地图、模块摘要、需求编号索引和关系。发现冲突后再请求相关正文。上下文装配器记录每项内容的来源、版本、哈希、纳入原因和裁剪状态。

### 7.3 大文件处理

来源文件按页读取。模块需求仍然过大时，先检查业务模块是否应该拆分；只有用户确认后才能调整地图和模块身份。不得通过任意截断隐藏重要内容。

## 8. 版本和修订

### 8.1 模块版本

业务模块使用稳定编号。候选版本记录父版本、文件列表、内容哈希、来源、变更摘要和影响。通过人工审核后形成模块需求已批准版本。

### 8.2 总需求版本

总需求版本精确组合：

- 产品概述版本；
- 需求地图结构版本；
- 各模块需求已批准版本；
- 各外部接口需求已批准版本；
- 全局和模块非功能需求已批准版本。

任何引用都必须使用精确编号和哈希，不得保存含糊的“最新”。

### 8.3 修订记录

每次语义变化追加修订记录。文字整理通常不使下游失效；语义澄清由人工确认影响；行为变化使相关设计、代码和测试失效；结构变化重新计算地图和依赖，并由生命周期状态重新推导项目进度。

AI 提出影响范围，插件根据引用计算直接和传递依赖，用户在审核时确认最终影响。

### 8.4 拆分和合并

模块拆分或合并时：

- 旧模块保留并标记退役；
- 新模块使用新稳定编号；
- 新模块记录来源于哪些旧模块；
- 需求条目保留稳定编号，无法保留时记录替代关系；
- 创建新的总需求版本；
- 相关设计、代码和测试按影响标记失效。

## 9. Skill 与插件分工

### 9.1 Skill 负责

- 阅读和理解相关资料；
- 生成产品概述、地图和模块草案；
- 识别冲突、推断和未知；
- 提出一个高影响问题；
- 提供有限候选、推荐和影响说明；
- 根据用户决定维护 Markdown；
- 执行跨模块场景走查和独立预审。

### 9.2 插件负责

- 来源快照和内容哈希；
- 路径和访问边界；
- 稳定编号、父子关系和引用校验；
- 地图结构和依赖校验；
- 候选文件清单和 SHA-256；
- 审核、已批准版本和修订记录；
- 影响传播和状态恢复；
- 禁止待办项或 AI 声明冒充正式事实。

插件不判断业务需求是否正确，也不解析自然语言待办项生成项目事实。

## 10. 对设计和测试的交付

模块需求已批准版本必须使 `/sdlc-design <业务模块名称>` 能确定或明确标记未知：

- 模块目标、范围和功能组；
- 角色、权限和公共行为；
- 数据、状态、错误和恢复要求；
- 外部接口和信任要求；
- 适用非功能需求；
- 依赖模块和跨模块场景；
- 验证方法和验收要点；
- 未知、阻塞和风险。

需求阶段不提前给出类、表、进程、目录或实现算法。这些由设计阶段决定。

## 11. 验证方案

### 11.1 确定性测试

- 重复模块、功能组或需求编号被拒绝；
- 地图引用不存在模块时被拒绝；
- 循环执行依赖被拒绝；
- 接口或非功能需求缺少作用范围时被拒绝；
- 无来源的技术和数值不能变成确定事实；
- 候选绑定全部文件和来源哈希；
- 任一文件变化后旧候选不可直接批准；
- 模块拆分、合并和退役保留历史关系；
- 文字布局变化不创建需求语义版本；
- Todo 完成不创建候选或已批准版本。

### 11.2 压力场景

1. 只提供“用户管理”页面，验证 AI 先恢复产品范围和“系统管理”上层模块；
2. 单个模块文件过大，验证 Skill 提出业务拆分候选而不是静默截断；
3. 两个模块引用同一外部接口，验证接口需求只维护一份；
4. 全局安全要求变化，验证所有适用模块被标记受影响；
5. 用户要求“按行业默认”，验证数值保持未知；
6. 候选后修改一个文件，验证旧候选与工作区不一致；
7. 会话中断，验证从地图、当前模块和开放问题恢复；
8. 模块拆分后，验证旧版本仍可重建；
9. 跨模块认证流程冲突，验证全局走查发现问题；
10. 大量模块存在时，验证单次上下文只读取目标模块和必要引用。

## 12. 当前实现情况

当前插件已经提供产品概述、需求地图、模块需求、接口需求、非功能需求和总需求版本合同；`/sdlc-spec` 按业务模块路由，最小上下文装配记录版本、哈希、纳入原因和裁剪状态。

需求地图工具校验业务模块和功能组身份、执行依赖、循环、外部接口以及非功能需求作用范围。全局非功能需求
在地图中只能有一个对象，避免多个批准版本同时拥有同一 `global.md`；分类由文档内稳定编号表达。候选工具校验
规定路径和章节，固定多文件字节快照；新上游版本会使旧总需求和下游状态自动失效。来源工具可以有界列出
授权资料目录，并把原型素材目录固定成一个不可变来源事实，目录中的文件使用条目哈希追溯而不产生大量来源 JSON。

本次实际产物中，产品概述约 6.9 KB、需求地图约 3.4 KB、两个模块需求约 7.5 KB 和 16.1 KB、接口需求
约 8.4 KB、全局非功能需求约 6.5 KB，总需求清单约 1.4 KB。拆分后单次上下文只装配当前一级业务模块
和必要引用，没有把整份需求一次性送入模型。隔离产品评审仍发现占位入口追溯、字段一致性和素材来源引用
缺口，证明结构完整不等于业务语义正确；这些问题必须通过需求修订和用户审核处理，不能由工具静默改写。

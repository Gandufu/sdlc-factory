# `/sdlc-design` 与测试验证设计

文档编号：DESIGN-03
状态：正式方案，核心合同已实现，等待完整目标项目验收
更新日期：2026-08-11

上位设计：[DESIGN-01《插件验证阶段总体设计》](./01-mvp0-opencode-plugin-design.md)
需求输入：[DESIGN-02《`/sdlc-spec` 模块化需求设计》](./02-mvp0-sdlc-spec-design.md)

## 1. 目标

本设计解决三个问题：

1. 设计文档不能重新变成一份需要一次性放入模型的巨型文档；
2. 测试需要有可审核的说明、真实运行记录和用户可读报告，不能只有测试代码或 AI 结论；
3. 系统测试应复用已经生成的测试代码和有效证据，Playwright 只验证跨模块完整行为，避免实时重复生成测试造成模型调用成本。

设计、编码和测试沿用需求阶段确定的业务模块，不产生新的能力单元。

## 2. 设计产物

```text
docs/design/
├─ product-architecture.md
├─ modules/
│  └─ system-management/
│     └─ design.md
├─ interfaces/
│  └─ <interface>.md
└─ design-set.yaml
```

### 2.1 产品总体设计

`product-architecture.md` 只描述跨模块共享内容：

- 系统边界和外部参与者；
- 模块关系和依赖方向；
- 运行进程、线程、并发和控制原则；
- 全局数据、事务和一致性原则；
- 认证、授权、凭据和信任原则；
- 部署、环境和资源原则；
- 失败、恢复、降级和审计原则；
- 系统测试和架构符合性原则；
- 全局设计决定、替代方案和风险。

它不复制每个模块的详细设计。

### 2.2 模块设计

每个业务模块维护一份 `design.md`，至少包含：

1. 输入的模块需求版本；
2. 模块目标和职责；
3. 包含和不包含范围；
4. 对外提供和依赖的接口；
5. 数据对象、所有权和一致性；
6. 状态、流程、并发和时序；
7. 错误、重试、幂等、恢复和降级；
8. 权限、信任和敏感数据处理；
9. 计划实现路径和测试路径；
10. 需求条目到设计和测试说明的追溯；
11. 开放问题、风险和替代方案；
12. 修订摘要。

模块设计可以包含内部类、包、进程、表和实现结构，但这些只是模块内部实现，不形成新的项目级执行单位。

### 2.3 接口设计

接口设计按外部系统、设备、协议合同或跨模块公共接口拆分，包含：

- 对应的外部接口需求版本；
- 协议和版本；
- 逻辑地址模板和路径；
- 请求、响应和事件结构；
- 认证和授权方式；
- 超时、重试、限流和熔断；
- 错误码和失败语义；
- 兼容和演进策略；
- 安全和审计要求；
- 契约测试方式。

接口设计不写死某一测试环境实际地址，也不保存明文凭据。

### 2.4 总设计版本

`design-set.yaml` 是用户可审阅的清单投影，精确组合：

- 产品总体设计已批准版本；
- 各模块设计已批准版本；
- 各接口设计已批准版本；
- 各模块测试说明已批准版本；
- 输入总需求版本；
- 内容哈希和父版本。

## 3. 测试产物

```text
docs/verification/
├─ modules/
│  └─ system-management/
│     └─ verification-spec.md
├─ system-verification-spec.md
└─ verification-report.md
```

测试领域分为四类事实：

| 产物 | 作用 | 是否手工维护 |
| --- | --- | --- |
| 测试说明 | 规定验证范围、方法、环境和通过条件 | 由 AI 辅助、用户审核 |
| 测试代码 | 可重复执行的单元、集成、契约和 Playwright 测试 | 随代码维护 |
| 测试记录 | 保存一次真实执行的输入、命令、结果和证据 | 系统自动生成 |
| 测试报告 | 汇总测试记录供用户审核 | 系统自动生成 |

测试报告不能脱离测试记录自行编辑为“通过”。

## 4. 模块测试说明

每个业务模块维护一份 `verification-spec.md`，包含：

- 输入的模块需求和模块设计版本；
- 需要验证的需求条目；
- 单元测试范围；
- 模块内部集成测试范围；
- 外部接口契约测试范围；
- 必要的界面模块测试；
- 测试数据和前置条件；
- 允许使用的替身、模拟器和真实依赖；
- 测试环境要求；
- 可执行测试代码位置；
- 通过、失败、跳过和阻塞判定；
- 期望证据类型和保留位置；
- 已知缺口和人工检查项。

测试说明不复制每个测试函数的实现步骤。低层细节以测试代码为准，测试说明负责需求追溯、范围和证据合同。

## 5. 系统测试说明

`system-verification-spec.md` 只描述跨模块和真实系统行为：

- 参与验收的业务模块；
- 必须有效的总需求和总设计版本；
- 必须有效的模块代码和测试结果版本；
- 系统启动和就绪条件；
- 测试环境和外部接口要求；
- 跨模块关键用户流程；
- 数据流、权限和失败恢复场景；
- Playwright 场景和测试代码位置；
- 非浏览器接口检查；
- 报告内容和系统验收条件。

系统测试说明不重复模块单元测试清单，只引用模块测试结果和需要重新执行的规则。

## 6. `/sdlc-design` 流程

### 6.1 输入门槛

`/sdlc-design <业务模块名称>` 至少需要：

- 目标模块需求已批准版本；
- 相关外部接口需求已批准版本；
- 适用非功能需求已批准版本；
- 产品总体设计当前版本或明确缺口；
- 目标项目和脚手架事实；
- 已登记的技术和接口来源。

缺少模块需求已批准版本时停止设计并推荐 `/sdlc-review`。产品总体设计尚未形成时，可以在同一命令中先补充与当前模块相关的全局设计，但不得静默决定未知需求。

### 6.2 最小设计上下文

处理“系统管理”时只装配：

```text
产品总体设计相关章节
+ 系统管理模块需求
+ 相关接口需求和接口设计
+ 适用非功能需求
+ 直接依赖模块摘要
+ 目标脚手架事实
+ 相关技术来源
+ 当前设计和开放问题
```

### 6.3 设计循环

每轮只解决一个会改变结构、数据、接口、错误或测试的重要问题：

```text
读取输入
→ 提取设计约束
→ 提出候选方案
→ 说明推荐、代价和未采用理由
→ 用户决定
→ 更新模块设计和测试说明
→ 执行追溯与一致性检查
```

设计和测试说明必须同步维护。新增一个可观察行为时，必须同时说明如何验证；新增一个接口或环境依赖时，必须同时说明测试需要什么配置和证据。

### 6.4 候选和审核

模块设计候选是一个受控包，至少包含：

- 模块设计文件；
- 模块测试说明；
- 相关接口设计文件；
- 输入需求版本；
- 文件清单和 SHA-256；
- 开放问题和风险；
- 确定性检查结果。

用户一次审核该包。通过后形成模块设计和测试说明已批准版本，生命周期状态随之更新；总设计批准后，项目进度会将该模块显示为可以进入编码。退回后产生新候选，不修改已批准历史。

## 7. 项目进度

项目进度不是独立文档或可修改计划，而是状态工具从生命周期事实实时推导的只读当前投影。总设计批准后，每个业务模块展示：

- 稳定编号和名称；
- 当前需求、设计、代码和测试版本号；
- 当前阶段和完成状态；
- 等待审核、挂起、阻塞或失效状态；
- 单元测试和模块测试的当前结果；
- 阻塞原因和唯一建议命令。

项目进度不拥有独立版本号，也不保存历史。需求地图和总设计保存模块及依赖；候选、审核、运行、测试记录和追加式事件保存历史；项目进度只读取这些事实并展示最新状态。删除项目进度投影后必须能够完整重建。

OpenCode 编码待办清单只拆解当前模块的一次编码过程，不改变生命周期事实或项目进度；命令结束时推荐下一条命令的单条待办也不属于项目进度。

## 8. 编码阶段的测试责任

`/sdlc-code <业务模块名称>` 不只生成产品代码，还必须：

- 在修改代码前调用 OpenCode 原生 `todowrite`，建立当前模块的编码待办清单；
- 按测试说明建立或更新测试代码；
- 使用项目原生工具执行编译和静态检查；
- 执行受影响的单元测试；
- 执行可以在编码环境完成的模块集成和契约测试；
- 保存命令、退出码和输出哈希；
- 对失败、跳过和阻塞保留真实原因。

编码待办清单至少覆盖输入核对、测试先行、代码实现、相关验证和差异检查。它必须随实际进度更新；没有执行结果或差异证据的步骤不能标记完成。运行结束时保存清单摘要和未完成原因，用于恢复同一会话，但它仍不是项目进度或人工审核结论。

`todowrite` 或 `todoread` 不可用时，编码运行必须在修改文件前进入阻塞状态，不得用普通文本计划冒充可维护的编码待办清单。

OpenCode 规划模式可以在编码前用于只读分析复杂改动。实际修改必须回到构建模式，并重新以编码待办清单约束执行；规划模式输出不能绕过模块设计审核。

测试代码与产品代码共同进入模块代码候选。测试代码不是临时提示词产物，不在系统测试阶段重新生成。

## 9. 模块测试执行

`/sdlc-test <业务模块名称>` 使用独立于编码叙述的测试上下文：

- 当前模块代码已批准版本；
- 当前模块测试说明已批准版本；
- 依赖模块代码版本；
- 环境配置；
- 实际测试代码；
- 最近测试记录和失效原因。

测试使用项目原生工具，例如 Java 项目使用其构建和测试命令，TypeScript 项目使用其配置的测试命令。插件不得强制所有项目使用同一种测试框架。

完成后生成不可变测试记录。用户审核测试记录和证据后形成模块测试结果已批准版本。

## 10. 测试记录

每次测试记录至少包含：

- 测试记录编号；
- 目标业务模块或系统范围；
- 总需求和总设计版本；
- 模块代码和测试说明版本；
- 依赖模块版本；
- 产品代码和测试代码哈希；
- 环境配置编号和哈希；
- 实际接口地址，敏感信息脱敏；
- 测试命令、工作目录和退出码；
- 开始、结束和持续时间；
- 通过、失败、跳过和阻塞数量；
- 测试框架和锁文件哈希；
- 日志、报告、截图、视频和跟踪文件位置；
- 是否复用历史证据及来源记录编号。

结构化记录是权威事实。Markdown 测试报告是它的用户可读投影。

## 11. 环境配置和接口地址

环境配置独立于需求和设计，至少包含：

- 环境编号、名称和用途；
- 应用地址、端口和就绪检查；
- 外部接口实际地址；
- 数据库和其他依赖地址；
- 依赖版本；
- 凭据引用；
- 生效时间和内容哈希。

接口需求说明为什么需要外部能力；接口设计说明协议和逻辑路径；环境配置保存实际地址；测试记录保存本次解析和使用的地址。

访问令牌只在受控执行器内取得和使用。系统可以记录签发方式、签发时间、过期时间和刷新结果，不保存明文令牌。

## 12. 证据复用和失效

成功测试记录只有在以下指纹完全一致时才能复用：

```text
模块代码哈希
+ 测试代码哈希
+ 模块需求版本
+ 模块设计版本
+ 测试说明版本
+ 接口和非功能需求版本
+ 依赖模块代码版本
+ 环境配置哈希
+ 工具链和锁文件哈希
```

任一项变化，相关记录标记失效。插件根据需求地图和实施依赖计算直接和传递影响。

复用只避免重复执行，不等于新的运行记录。系统验收报告必须明确哪些结果是本次执行、哪些结果是基于相同指纹复用。

## 13. 系统测试

`/sdlc-test system` 执行以下固定顺序：

1. 固定参与验收的总需求、总设计以及各模块代码和测试结果版本；
2. 检查每个模块代码和测试结果是否有效；
3. 使用原生测试命令重新执行失效或受影响模块测试；
4. 启动完整应用；
5. 等待健康检查和业务就绪检查通过；
6. 检查数据库、消息系统和外部接口连通性；
7. 执行接口契约和非浏览器系统检查；
8. 使用 Playwright 执行跨模块关键用户流程；
9. 汇总执行和复用记录；
10. 生成系统测试报告并停止等待人工审核。

### 13.1 Playwright 的范围

Playwright 负责：

- 浏览器中的真实用户流程；
- 前端、后端、数据库和外部接口协同；
- 跨模块权限和状态变化；
- 关键失败、恢复和错误提示；
- 必要的截图、视频和跟踪证据。

Playwright 不负责：

- 执行 Java 或 TypeScript 单元测试；
- 替代数据库和接口契约测试；
- 在应用尚未就绪时反复重试掩盖启动失败；
- 现场让 AI 重新生成所有测试。

## 14. 测试报告和系统验收

系统测试报告由结构化测试记录自动生成，至少包含：

- 本次验收范围和输入版本；
- 环境和实际接口地址摘要；
- 各模块测试结果；
- 本次重新执行和复用的记录；
- Playwright 场景结果；
- 失败、跳过、阻塞和未提供证据；
- 证据文件位置；
- 已知风险和人工检查项；
- 报告内容哈希。

只有以下条件同时满足，用户才能批准系统验收：

- 参与范围内所有模块代码和测试结果当前有效；
- 必须场景没有失败、跳过或阻塞；
- 外部接口和环境证据满足测试说明；
- Playwright 关键流程通过；
- 报告绑定全部底层测试记录；
- 用户明确审核当前报告编号和完整 SHA-256。

## 15. 模型调用成本控制

测试执行本身不需要模型参与。成本控制规则：

- 测试代码在模块编码期间生成并版本化；
- 受控执行器直接运行测试命令；
- 测试结果先由确定性解析器转成结构化摘要；
- AI 只在诊断失败时读取相关模块、失败摘要和有限日志；
- 不把完整日志、截图、视频和 Playwright 跟踪文件放入模型上下文；
- 完全相同指纹的成功记录可以复用；
- 同一根因重复失败时暂停并请求人工处理，不无限重试。

## 16. 版本和影响传播

模块需求变化后：

- 相关模块设计和测试说明标记失效；
- 相关代码和测试结果按影响标记失效；
- 依赖模块根据关系传播；
- 总需求和总设计按变化产生新版本，项目进度根据新的生命周期事实重新计算。

只有测试说明补充且不改变产品行为时，可以复用同一模块设计正文，但仍需形成新的设计包版本并重新执行受影响测试。

接口或非功能需求变化时，只影响作用范围内模块。产品总体设计变化时，系统必须根据设计引用计算受影响模块，不能默认所有模块都通过或全部失效。

## 17. 安全和失败保真

- 环境配置不得包含明文凭据；
- 日志和报告必须对令牌、密码和个人信息脱敏；
- 测试工具只访问明确允许的地址和目录；
- 外部接口不可用时记录阻塞，不使用模拟结果冒充真实通过；
- 真实环境未执行的测试记录为未提供证据；
- 失败记录不可覆盖，修复后产生新的测试记录；
- AI 不得修改测试记录或系统生成的报告结论。

## 18. 验收场景

1. 模块设计只加载对应需求和必要引用；
2. 设计候选同时绑定模块设计和测试说明；
3. 实际接口地址只来自环境配置；
4. 测试记录保存实际地址但不泄露凭据；
5. 单元测试由项目原生工具执行；
6. Playwright 只在应用就绪后执行跨模块场景；
7. 相同指纹复用成功记录，不同指纹拒绝复用；
8. 修改测试代码使旧记录失效；
9. 修改全局安全需求只影响作用范围内模块；
10. 系统报告可以追溯到每条底层记录和证据；
11. 完整日志不进入模型上下文；
12. 失败、跳过、阻塞和未提供证据不会变成通过。

## 19. 当前实现情况

当前插件已经实现产品总体设计、模块设计包、接口设计和总设计版本合同。模块设计包同时绑定测试说明和批准的产品/测试路径边界。编码运行必须先建立 OpenCode 原生待办，受控命令自动保存真实证据；测试记录按输入版本、环境和文件指纹生成，测试报告只从结构化记录汇总。
